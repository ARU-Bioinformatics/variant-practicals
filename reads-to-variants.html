Reads to variants: does this person carry CYP2C19*2?

You will take raw sequencing reads from a human exome and turn them into a list of genetic variants – checking the reads, aligning them to the reference genome, sorting and indexing the alignments, calling and filtering variants – and finish by finding one variant that matters for prescribing: CYP2C19*2. You will run the pipeline twice: by typing commands, and in a Galaxy-style workflow engine.

About 2½ hoursNo software to installChrome, Edge, Firefox or Safari on a laptop or desktop
The clinical question

Clopidogrel is an antiplatelet drug given after heart attacks, stents and strokes. It is a prodrug: liver cytochrome P450 enzymes – mainly CYP2C19 – convert it to the active metabolite that blocks the platelet P2Y12 receptor. People who carry a no-function CYP2C19 allele make less active drug and are at higher risk of clots on standard treatment. The commonest no-function allele, CYP2C19*2 (rs4244285), is carried on about 15% of chromosomes in Europeans and 30–36% in East and South Asians (1000 Genomes). Guidelines now recommend genotype-guided prescribing – for example CPIC for acute coronary syndromes and NICE (DG59) after ischaemic stroke or TIA.

Your job: start from the raw reads of one person and find out whether she carries CYP2C19*2 – and how confident you can be.

The data

The person is NA12878, a woman from a Utah family of northern and western European ancestry (CEPH collection) whose DNA has been sequenced more times than anyone else's. Her genome is the reference sample that laboratories use to test their pipelines (HapMap, 1000 Genomes, Genome in a Bottle). You have exome reads – DNA fragments captured from the exons – sequenced on an Illumina machine as paired-end 76-base reads. To keep things fast we only give you the read pairs from the region of chromosome 10 that holds the CYP2C gene cluster (CYP2C18, CYP2C19, CYP2C9, CYP2C8) – about 150,000 pairs instead of tens of millions.

1.2 Inside a FASTQ file

Sequencers write reads in FASTQ format. The files are big, so they are almost always gzip-compressed (.gz). zcat uncompresses a file on the fly, and the pipe | sends its output straight into the next program – here head, which keeps the first lines.

How long are the reads (in bases)?

76 bases – every read in these files is 76 long (FastQC's Basic Statistics agrees).

The second read in file 1 ends in #######. What quality is that, and what should an aligner or variant caller do with those bases?

# is ASCII 35 → Q2: a 63% chance of being wrong, i.e. no real information. Illumina's software marks the unreliable end of a read this way. The bases should count for (almost) nothing: BWA-MEM can soft-clip poor ends that do not match, and variant callers weight every base by its quality – bcftools ignores bases below Q13 by default. Trimming the tails off before alignment is another option.

The first reads of the two files have the same name except for /1 and /2. What does that tell you, and why is sequencing both ends of each fragment useful?

They are the two ends of the same DNA fragment (a read pair): read 1 from one end, read 2 from the other end on the opposite strand. Pairs are useful because the two reads must map close together, facing each other: that places reads in repeats and paralogous genes that a single short read could not place, flags poorly mapped reads, estimates the fragment (insert) size, and reveals structural variants when pairs map too far apart or in the wrong orientation. The files must stay in the same order – read n of file 1 pairs with read n of file 2.

How many reads are in file 1?

612,720 lines ÷ 4 = 153,180 reads (and the same number in file 2: 153,180 pairs, 306,360 reads in all).

grep -c '^@' gave a bigger number than the number of reads. Why? What does this teach you about checking your commands?

@ is also a quality character (Q31), so some quality lines (line 4) start with @ too – here 24,186 of them in file 1. '^@SRR' only matches read names and gives the right answer, 153,180. Lesson: a command that runs without an error can still give a wrong answer – check results against something you know (here, lines ÷ 4). Programs that understand the format (FastQC, seqkit stats) are safer.

Quality control with FastQC

Work down each report (click a module in the summary box to jump to it; each has a short explanation). Hover over the plots to read the values.

  • Basic Statistics – number of reads, read length, GC content and the quality encoding.
  • Per base sequence quality – box plots of quality at each position along the reads. Green, orange and red bands mark very good (≥ 28), reasonable and poor (< 20) quality.
  • Sequence Duplication Levels and Adapter Content – signs of PCR over-amplification and of fragments shorter than the reads.
Which file has a Fail, in which module – and what does the plot show?
Why does quality fall along the reads, and why is read 2 usually worse than read 1?

Illumina sequencing reads one base per chemistry cycle. In each cycle a few molecules in a cluster fail to extend or extend twice, so the copies in a cluster drift out of step (phasing and pre-phasing); the signal gets noisier with every cycle and the quality scores fall. Read 2 is sequenced after read 1 and after the fragments have been re-synthesised on the flow cell, so its clusters have been through many more cycles and chemistry steps – it is typically worse.

Would you trim these reads before aligning them? Give one reason for and one against.

For: about a fifth of the read 1s and nearly a third of the read 2s end in a run of Q2 (#) bases; trimming them removes noise and helps some aligners. Against / not essential here: BWA-MEM does local alignment and soft-clips ends that do not match; bcftools discards bases below Q13 and weights the rest by quality, so the poor tails hardly affect the calls. Adapter content is below 1%, so adapter trimming is not needed. Many pipelines trim anyway (e.g. fastp, Trimmomatic, Cutadapt); what matters is to decide, and to record the decision.

FastQC estimates that about 79% of the reads would remain if exact duplicates were removed. Why do exome data usually show some duplication, and what do pipelines do about it?

Exome libraries are amplified by PCR and the captured targets are sequenced very deeply, so many reads are copies of the same original fragment (and deep sequencing of a small target also produces some identical fragments by chance). Duplicates are not independent evidence, and a PCR error copied many times can look like a variant. Pipelines therefore mark duplicates after alignment (e.g. samtools markdup, Picard MarkDuplicates), and callers such as bcftools ignore reads flagged as duplicates. We skip that step today to keep the pipeline short – it is one of the “clean-up” steps a production pipeline adds.

Aligning the reads to the genome

≈ 20 minWorkbench: Terminal

A read on its own is 76 letters with no address. Alignment (or mapping) finds where in the reference genome each read comes from, allowing for sequencing errors and for real differences – the variants we are looking for.

Genome builds

The human reference is updated from time to time, and positions change between versions. hg19 (UCSC name) = GRCh37 (Genome Reference Consortium name), released in 2009; the current build is GRCh38/hg38 (2013). CYP2C19*2 is at chr10:96,541,616 on GRCh37 but chr10:94,781,859 on GRCh38. Use one build for everything – reads, annotation and databases. Your coursework data are aligned to hg19, so this practical uses hg19 too (and so should VEP and gnomAD when you look variants up: choose GRCh37).

3.2 The index

Scanning 3.1 billion bases for each of 300,000 reads would take far too long, so aligners first build an index of the genome. BWA builds an FM-index, a compressed index based on the Burrows–Wheeler transform (the same transform the bzip2 compression program uses): with it BWA can find where any short sequence occurs in the genome almost instantly. The index files sit next to the reference: hg19.fa.amb, .ann, .bwt, .pac and .sa.

Activity 3.2 · Index (already done)
  1. Type the indexing command to see what happens: bwa index ref/hg19.fa

3.3 Align with BWA-MEM

bwa mem takes the reference (it finds the index files from the name) and the two read files, and writes alignments in SAM format to the screen. The redirect > sends that output into a file instead. Messages about progress go to a separate channel (standard error), so they still appear on screen.

Activity 3.3 · Run the alignment

  2. While it runs, read the messages. BWA reads the pairs in batches and, from the pairs that map uniquely, estimates the size of the DNA fragments (the insert size).
What is the mean insert size (fragment length) BWA estimated? Give the number in bp.

About 169 bp (standard deviation about 64 bp; median 158 bp). Two 76-base reads cover 152 bases, so nearly half of the fragments are short enough for the two reads to overlap in the middle – the same bases are read twice, once from each end. Adapter sequence appears only when a fragment is shorter than a single read (76 bases), which is rare.

Sort, index and summarise

≈ 15 minWorkbench: Terminal

The SAM file lists the reads in the order they came off the sequencer. To look at – or call variants in – one region, programs need the reads sorted by position, stored compactly as BAM (binary, compressed SAM), and indexed (a .bai file that says where in the BAM each region starts).

Activity 4.1 · Make a sorted, indexed BAM
  1. Sort by position and write BAM: samtools sort -o results/aligned.sorted.bam results/aligned.sam
  2. Index it: samtools index results/aligned.sorted.bam – this runs the real samtools in your browser.
  3. Compare the sizes: ls -lh results
How big are the SAM and the BAM files? Why do we keep BAM rather than SAM?

SAM ≈ 77 MB, sorted BAM ≈ 22 MB – about 3.5 times smaller. BAM is compressed binary (blocks of gzip, “BGZF”), so it is smaller and faster to read, and – once sorted and indexed – programs can jump straight to any region instead of reading the whole file. A full human exome BAM is typically 5–15 GB; the SAM would be several times larger.

What happens if you do the steps in the wrong order? Try samtools index results/aligned.sam and read the error. Error messages are clues, not failures.

How many reads mapped to chr10?

300,965 – 99.3% of the mapped reads.

These reads were chosen because they came from chromosome 10. Why have some mapped to other chromosomes?

About 2,000 reads (0.7% of the mapped reads) landed elsewhere – a few dozen to a couple of hundred per chromosome. 3,516 reads did not map at all: most are listed beside their mapped mate (idxstats' last column), and 390 from pairs where neither read mapped are on the * line. The reads were chosen because the 1000 Genomes pipeline had placed them in chr10:95–98 Mb, but a short read that matches several places equally or almost equally well (repeats such as Alu and LINE elements, pseudogenes, related genes) can be placed differently by another aligner version or reference build. Most of these reads have low mapping quality, and very few pass the depth filter when variants are called. With a whole exome, the same effect spreads a few reads from every gene across the genome.

Calling variants

≈ 25 minWorkbench: Terminal

At every position, the reads either agree with the reference or show another base. A variant caller weighs that evidence – how many reads, how good their bases and mappings are – and decides the most likely genotype: two copies of the reference allele (0/0), one of each (0/1, heterozygous) or two copies of the other allele (1/1, homozygous).

Two steps in bcftools

bcftools mpileup “piles up” the reads at every covered position and computes genotype likelihoods: how probable the reads would be if the genotype were 0/0, 0/1 or 1/1. bcftools call combines those likelihoods with a prior and reports the variant sites and their most likely genotypes. Because the pile-up has a line for every covered base (millions), it is piped straight into call rather than saved.

5.1 Run the caller

Activity 5.1 · mpileup | call
  1. First, peek at the pile-up for five bases around the CYP2C19*2 position: bcftools mpileup -a AD,DP -f ref/hg19.fa -r chr10:96541614-96541618 results/aligned.sorted.bam | grep -v '^##'. Look at the line for 96541616: the ALT column offers A and the AD tag counts the reads for each allele.
  2. Now call variants across all the reads (about a minute in the browser): bcftools mpileup -Ou -a AD,DP -f ref/hg19.fa results/aligned.sorted.bam | bcftools call -mv -Ov -o results/calls.vcf

How many variants did bcftools call?

2,744. That is far more than the region's exons could hold – many are unreliable calls from a handful of reads. Next we filter.

5.3 Filter the calls

A raw call set always contains false positives: calls made from one or two reads, calls in reads that map badly, sequencing or PCR errors. The simplest filters require a minimum call quality and read depth.

Activity 5.3 · Keep the confident calls
  1. Keep calls with QUAL ≥ 30 and at least 10 reads: bcftools view -i 'QUAL>=30 && INFO/DP>=10' results/calls.vcf > results/calls.filtered.vcf
  2. Count what is left (↑ and edit the earlier grep).
How many variants pass the filter?

218 of 2,744 (8%). Most of the removed calls had fewer than 10 reads: exome capture pulls down the exons strongly, but some reads come from off-target DNA around them, where coverage is thin.

Filtering is a trade-off. What do you lose by making the thresholds stricter (say QUAL ≥ 100 and DP ≥ 30)? When might you accept that?

Stricter filters remove more false positives but also more true variants (lower sensitivity) – especially in regions with low coverage, which in an exome include the ends of exons and GC-rich exons. For a diagnostic search you usually want high sensitivity and then check candidates by eye (IGV) or by another method (Sanger sequencing); for a large research set you may prefer high specificity. The filter thresholds are part of your methods and must be reported.

5.4 Find CYP2C19*2

Activity 5.4 · The answer to the question
  1. Search the filtered calls for the position: grep -w 96541616 results/calls.filtered.vcf (-w: whole word)
What are the REF and ALT alleles, and the genotype (GT)? How many reads support each allele (AD)?

REF G, ALT A, GT 0/1 – heterozygous. AD = 44,48: 44 reads carry G and 48 carry A, close to the 50:50 expected for a heterozygote. QUAL is 222 – as high as bcftools usually goes (confident calls top out around 220–230). NA12878 carries one copy of CYP2C19*2.

One copy of a no-function allele: what would you predict for NA12878's clopidogrel response? What else would you want to check before saying so in a report?

With one no-function allele she is most likely a CYP2C19 intermediate metaboliser (e.g. *1/*2): less active metabolite, weaker platelet inhibition; CPIC advises an alternative (prasugrel or ticagrelor) after ACS/PCI if there is no contraindication. Before reporting you would check: the call in the reads (IGV); other CYP2C19 alleles – e.g. *3, and the increased-function *17 in the promoter, which an exome may not cover (no call is not the same as a reference genotype); and ideally confirm with an independent method. Activity 5.5 · bcftools query and FreeBayes
  1. bcftools query prints chosen fields: bcftools query -f '%CHROM\t%POS\t%REF\t%ALT\t%QUAL\t[%GT\t%AD]\n' results/calls.filtered.vcf | head

Do the two callers agree about CYP2C19*2? Do they find the same number of variants? Why might they differ?

Both call chr10:96541616 G>A as heterozygous. FreeBayes with default settings reports 4,142 sites – it reports almost any candidate and leaves filtering to you; with --standard-filters --min-coverage 10 (Galaxy's “simple diploid calling with filtering and coverage”) it reports 268. The callers use different models (bcftools: per-position genotype likelihoods; FreeBayes: short haplotypes, so neighbouring variants and indels are described differently) and different default read and base filters, so call sets differ mostly at low-coverage and messy sites. Pipelines are usually compared on a truth set – for NA12878, the Genome in a Bottle benchmark calls.

Which amino acid is encoded at the variant, and what is its number?

Proline 227 (P227), near the start of exon 5. CYP2C19 is on the plus strand here (transcribed left to right), so you read the codon directly: CCG → CCA. Both codons encode proline – the change is synonymous.

The same analysis in a workflow engine

≈ 30 minWorkbench: Workflow engine

A workflow engine runs a chain of tools for you and records exactly what was done. Galaxy (usegalaxy.eu, usegalaxy.org) does this through a web page: you pick tools from menus instead of typing, every result is kept in a history, and a sequence of steps can be saved as a workflow and re-run on new data with one click. Research groups also use code-based workflow managers such as Nextflow and Snakemake, where the workflow is a script. The engine on this page is a small Galaxy look-alike that runs the same programs as your terminal.

Compare Galaxy's command line with the one you typed in chapter 2. What is the same? What did Galaxy add, and why?

The core is the same program: fastqc on the same file. Galaxy first links the dataset into a job folder under a readable name (ln -s …dataset_1.dat NA12878_chr10_R1.fastq.gz), then adds options for running unattended on a server: --outdir ., --threads (the processors it was given), --quiet, --extract (unzip the results so the raw data can become a second output) and -f fastq (don't guess the format from the name). Finally it copies the outputs to the dataset files shown in the history. Every result in Galaxy carries this record – its provenance.

Why did the engine refuse the first connection? How does this help you?

Every dataset has a type (fastqsanger.gz, bam, bcf, vcf, html…) and every tool input accepts only certain types. An HTML report cannot be filtered as a VCF, so the connection is refused. Type checking catches mistakes when you build the workflow, not hours later when a job fails – one of the safety nets a workflow engine gives you (on the command line nothing stops you from giving a program the wrong file).

How many variants are in the workflow's filtered VCF – the same as your command-line result? Why?

218 – identical, because the workflow ran the same programs, with the same versions, on the same data and reference, with the same parameters. The only difference is that Galaxy's BWA-MEM step pipes straight into samtools sort (no SAM file is kept), which does not change the alignments. (One subtlety: Galaxy runs BWA-MEM with two threads. BWA-MEM reads its input in batches whose size depends on the number of threads and estimates the insert size batch by batch, so on a real server a handful of alignments can differ between thread counts unless the batch size is fixed with -K. Here the engine re-uses the terminal's alignments, so they match exactly.) Same inputs + same tools + same parameters = same result: that is reproducibility – and a workflow engine records all three for you.

Your history is a script

Type history in the terminal. The commands that worked, in order, are your pipeline. Saved in a file they become a script that anyone can re-run:

#!/bin/bash
# reads-to-variants.sh – NA12878, CYP2C region, hg19
set -euo pipefail
fastqc -o results data/NA12878_chr10_R1.fastq.gz data/NA12878_chr10_R2.fastq.gz
bwa mem ref/hg19.fa data/NA12878_chr10_R1.fastq.gz data/NA12878_chr10_R2.fastq.gz > results/aligned.sam
samtools sort -o results/aligned.sorted.bam results/aligned.sam
samtools index results/aligned.sorted.bam
bcftools mpileup -Ou -a AD,DP -f ref/hg19.fa results/aligned.sorted.bam | bcftools call -mv -Ov -o results/calls.vcf
bcftools view -i 'QUAL>=30 && INFO/DP>=10' results/calls.vcf > results/calls.filtered.vcf
Activity 8.1 · Reflect

A clinical lab must analyse 200 exomes a month and show an inspector exactly how every result was produced. A PhD student wants to try five aligners with different settings on one sample. Which approach suits each, and why?

Clinical lab: a fixed, validated, version-controlled pipeline run by a workflow system (Galaxy, or Nextflow/Snakemake on a cluster) – automatic provenance, the same steps every time, easy to audit, scales to many samples. PhD student: the command line (or a notebook/script) – maximum flexibility to change tools and options quickly; once the best combination is found, it can be captured in a script or workflow. Both need records: a lab's standard operating procedure, a student's scripts and notes.
